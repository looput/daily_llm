# When the Specification Emerges: Benchmarking Faithfulness Loss in Long-Horizon Coding Agents

**arXiv**: [2603.17104](https://arxiv.org/abs/2603.17104) · [PDF](https://arxiv.org/pdf/2603.17104)  
**领域**: Agent  
**作者**: Yan, Chen, Zhang

## 摘要

> 本文针对当前编码智能体评测中任务规范一次性给定的局限性，提出了一个新颖的评测基准，用于研究在长期交互中任务规范逐步显现（Emergent Specification）场景下智能体的忠实度损失问题。论文定义了SLUMP指标，并构建了包含20篇近期顶级会议论文、371个可验证组件的基准。实验评估了Claude Code和Codex等主流模型，发现规范逐步显现确实会导致实现忠实度显著下降。作为缓解方案，论文提出了ProjectGuard这一外部项目状态跟踪层，并在实验中验证了其有效性。作者团队未明确标注所属知名机构。

## 详细分析

> **社区热度**: ⭐ 1 (来自 papers.cool)

## 问题定义

这篇论文试图解决的核心问题是：**在长时程（long-horizon）编码任务中，当目标系统规范通过多轮交互逐步"涌现"（emergent specification）而非在开始时完整提供时，AI编码代理难以有效跟踪和保持设计承诺，导致最终代码实现与预期设计之间的忠实度下降。**

具体而言，论文关注以下几个关键层面：

### 1. 现有基准测试的局限性
当前主流的编码代理基准测试（如 PaperBench、MLRBench 等）普遍假设**完整的任务规范在会话开始时即已 upfront 提供**（无论是论文、任务描述还是测试套件）。然而，真实的研究编码工作流程往往不符合这一假设——研究者通常从模糊的想法开始，通过多轮探索、实现和迭代 refinement 逐步明确系统设计。

### 2. SLUMP 现象的识别与量化
论文定义并研究了 **SLUMP（Faithfulness Loss Under Emergent Specification，涌现规范下的忠实度损失）**：

$$\text{SLUMP}_F(p, a) = F(R_{p,a}^{\text{ss}}) - F(R_{p,a}^{\text{em}})$$

其中 $R^{\text{ss}}$ 表示一次性获得完整规范时的实现，$R^{\text{em}}$ 表示通过交互逐步获得规范时的实现。正值表明**渐进式规范披露会降低最终实现的忠实度**。

### 3. 忠实度损失的两个诊断维度
论文将 SLUMP 分解为两个关键维度进行诊断：
- **语义忠实度（Semantic Faithfulness）**：最终代码是否正确实现了承诺的算法内容
- **结构整合（Structural Integration）**：后期代码是否保留并复用了早期实现的模块，而非绕过或以不兼容的方式重新实现

### 4. 规范跟踪（Specification Tracking）的挑战
核心难点在于代理必须在长会话中维护**项目级规范状态**（project-level specification state），包括持久的设计承诺（如数学公式、架构约束、接口契约等），并在代码库演进过程中保持这些承诺。现有系统在处理分布式、渐进式披露的设计规范时表现出明显的忠实度损失。

### 5. 缓解策略的探索
作为案例研究，论文提出了 **ProjectGuard**——一种外部项目状态层，通过维护语义状态（设计承诺）和结构状态（代码库组织）来支持规范跟踪，实证显示可恢复 90% 的忠实度差距。

简而言之，该论文识别了**"规范涌现"场景下的实现忠实度损失**作为一个被现有基准忽视但实践中至关重要的评估维度，并提供了相应的基准测试框架和缓解方法。

## 相关工作

该论文在第6节"Related Work"及相关章节中讨论了以下相关研究领域：

## 1. 交互式与项目级编码基准测试

**交互式编码环境**
- **InterCode** (Yang et al., 2023): 引入带执行反馈的标准化交互式编码基准测试。

**项目级代码生成**
- **ProjectEval** (Liu et al., 2025)、**RepoExec** (Le Hai et al., 2025)、**FEA-Bench** (Li et al., 2025b): 评估基于固定任务描述或提供仓库上下文的项目级/仓库级代码生成能力。

**多轮迭代代码生成**
- **CodeFlowBench** (Wang et al., 2025) 和 **SR-Eval** (Zhan et al., 2025): 研究迭代分解或逐步需求精化下的多轮代码生成。

## 2. 研究导向的代码实现基准测试

**基于论文的代码复现**
- **PaperBench** (Starace et al., 2025)、**LMR-BENCH** (Yan et al., 2025)、**ResearchCodeBench** (Hua et al., 2025)、**RECODE-H** (Miao et al., 2025): 评估将论文转化为可运行代码的能力，但这些基准测试通常假设论文、掩码仓库目标或结构化任务反馈在会话开始时即对代理可见。
- **MLR-Bench** (Chen et al., 2025): 将评估范围扩展到超越单纯编码的开放端机器学习研究工作流程。

**该论文的区别**: 上述基准测试通常提供完整的初始规范（论文或任务描述），而该论文研究的"涌现规范"设置中，目标设计基于论文但**从不 upfront 展示**，必须通过多轮交互逐步推断和整合。

## 3. 长时程上下文管理与仓库状态维护

**上下文级别管理**
- 探索简单掩码 vs. 摘要、gist风格记忆、激活级压缩等方法。
- **Context Folding** (Sun et al., 2025)、**AgentFold** (Ye et al., 2025)、**MEM1** (Zhou et al., 2026): 学习上下文管理机制，用于处理长时程交互中的上下文窗口限制。

**仓库级别记忆与检索**
- **Think-Search-Patch** (Xiong et al., 2025): 通过检索增强推理框架进行仓库级代码修复。
- 仓库记忆方法和结构感知检索方法: 通过恢复文件、提交、问题或结构图中的相关上下文来改进代码修复或生成。

**上下文重用与保留评估**
- **SWE-ContextBench** (Zhu et al., 2026) 和 **LoCoEval** (Liu et al., 2026): 专门评估仓库导向任务序列中的上下文学习和保留能力。

**该论文的补充**: 该论文强调需要跟踪的不仅是仓库或早期观察中潜藏的状态，还包括**用户随时间新提交的设计知识**（specification tracking），这与上述上下文管理研究形成互补。

## 4. 超越执行指标的评估方法

**细粒度忠实度评估**
- **Agent-as-a-Judge** (Zhuge et al., 2025): 为开发任务提供需求级评估。
- **LLM critics for code changes**: 研究无需执行的仓库补丁评估。
- **SciCoQA** (Baumgärtner and Gurevych, 2026): 专注于科学论文与代码库之间的差异检测。

**该论文的贡献**: 遵循相同动机（执行指标过于粗糙），但针对**最终仓库对渐进式披露、论文衍生设计的忠实度**这一不同评估对象。

## 5. 规范跟踪与涌现规范

- **Zhu et al., 2026** 和 **Liu et al., 2026**: 在引言中提到，涉及代理在长会话中保留持久设计承诺并随代码库演进保持这些承诺的规范跟踪（specification tracking）能力。

这些相关研究表明，该论文填补了一个特定空白：**在规范非 upfront 提供、而是通过长时程交互逐步涌现的场景下，评估和维护代码实现对设计规范的忠实度**。

## 解决方案

论文通过**构建评估基准、分解损失维度、设计外部状态层**三个层面系统性地解决 SLUMP（涌现规范下的忠实度损失）问题：

## 1. 构建专用基准测试以量化问题

首先建立了一个针对"涌现规范"场景的评估框架，包含：

- **20篇近期ML论文**（ICML 2025和NeurIPS 2025各10篇），涵盖371个原子化可验证组件
- **渐进式交互脚本**：每篇论文生成约60个编码请求，模拟从模糊想法到完整设计的渐进披露过程，且**不透露原始论文**
- **五级忠实度评分标准**：
  - 0（Absent）：无实现尝试
  - 1（Wrong）：实现逻辑与规范不符
  - 2（Simplified）：降级或近似实现
  - 3（Equivalent）：形式不同但功能等价
  - 4（Faithful）：与预期设计和架构实现紧密匹配
- **暴露审计（Exposure Audit）**：验证评分组件确实可从可见交互中推断（恢复率 RCR=99.4%，显式规范率 ESR=66.6%），确保评估公平性

通过对比**涌现规范（emergent）**与**一次性规范控制（single-shot）**两种条件下的实现差异，论文量化了 SLUMP：

$$\text{SLUMP}_F(p, a) = F(R_{p,a}^{\text{ss}}) - F(R_{p,a}^{\text{em}})$$

## 2. 分解损失维度以诊断问题

论文识别出 SLUMP 的两个诊断维度，为针对性缓解提供依据：

| 维度 | 测量指标 | 问题表现 |
|------|----------|----------|
| **语义忠实度** | Mean Component Faithfulness (MCF) | 算法内容实现不准确或简化 |
| **结构整合** | Dependency Integration Ratio (DIR) | 后期代码绕过或重新实现早期模块，而非复用 |

实验发现：Claude Code 在两个维度均显著下降，而 Codex 主要损失体现在结构整合上。这种差异表明需要**同时维护设计承诺（语义）和代码组织（结构）**的解决方案。

## 3. 设计 ProjectGuard 外部状态层以缓解问题

作为针对性缓解的案例研究，论文提出 **ProjectGuard**——一种独立于底层模型的外部项目状态管理系统，通过以下机制恢复忠实度：

### 3.1 双状态维护架构

**语义状态（Semantic State）**
- 记录**设计承诺**（高层次方法结构、架构约束）、**决策**（接口约定、训练选择）和**资源**（经验观察、支持证据）
- 采用轻量级文件系统原生的图表示（节点+边表），支持局部更新和透明差异比较
- **保守更新策略**：仅记录用户请求和已接受项目进度中确认的承诺，而非每个助手提议

**结构状态（Structural State）**
- 记录仓库骨架：现有文件、类/函数签名、接口事实
- 通过 Git 历史直接派生，而非依赖代理的文本描述，确保与实际代码一致

### 3.2 兼容性感知预测与主动重启

**预测器（Forecaster）**
在每次编码轮次前，结合以下信息生成任务简报：
- 当前请求与历史请求序列
- 语义状态（哪些设计承诺相关）
- 结构状态（哪些模块可复用或需修改）

**主动重启（Proactive Restart）**
当预测器估计剩余实时上下文不足以支持即将到来的复杂集成任务时，触发新会话并注入渲染后的项目简报（包含当前语义和结构状态），避免上下文压缩导致的信息丢失。

## 4. 实验验证效果

在 Claude Code（SLUMP 较严重的平台）上的验证显示：
- **MCF 恢复**：从 2.718（涌现）提升至 3.000（ProjectGuard），恢复 90% 与一次性规范的差距（3.031）
- **完全忠实组件**：从 118 个增至 181 个（+53%）
- **严重失败**：从 72 例降至 49 例（-32%）
- **IF50 综合指标**：在 20 篇论文中的 15 篇上取得正向恢复

在 Codex 上，虽然语义损失较小，ProjectGuard 仍将 **DIR 提升 76%**，证明结构状态管理在改善模块整合方面的有效性。

该解决方案表明：**通过显式维护项目级语义和结构状态，而非依赖对话历史的隐式压缩，可显著减少涌现规范场景下的忠实度损失**，且无需修改底层模型架构。

## 实验验证

论文进行了以下四个层面的实验，系统性地验证 SLUMP 的存在、诊断其成因，并评估缓解方案：

## 1. 基准构建验证实验

在正式评估代理性能前，论文首先验证基准测试的**公平性**和**评分可靠性**：

### 1.1 暴露审计（Exposure Audit）
验证评分组件确实可从可见交互中推断，而非对代理"不公平地隐藏"。
- **方法**：人工标注每个组件的可恢复性等级 $R(c) \in \{0,1,2,3,4\}$，其中 $R\geq 1$ 表示至少可弱推断，$R=4$ 表示显式指定
- **指标**：
  - 可恢复组件率（RCR）：$ \text{RCR} = \frac{1}{|C|}\sum_c \mathbb{1}[R(c) \geq 1] $
  - 显式指定率（ESR）：$ \text{ESR} = \frac{1}{|C|}\sum_c \mathbb{1}[R(c) = 4] $
- **结果**：宏观平均 RCR = **99.4%**（358/371组件可恢复），ESR = **66.6%**（Figure 1）。证实组件需跨轮次整合推断，但非不可达。

### 1.2 评分校准（Score Calibration）
验证自动评判员与人工标注的一致性。
- **样本**：120个组件-运行对，分层采样自不同论文、平台和分数等级
- **方法**：两名独立标注员盲评，与自动评判员（最多8次工具调用）对比
- **结果**（Table 2）：
  - 加权 Cohen's $\kappa$：0.882–0.927（标注员 vs 评判员），0.930（标注员间）
  - 精确匹配准确率：86.7%–91.7%
  - ±1分范围内一致性：96.7%–99.2%

## 2. 主实验：SLUMP 量化对比

核心实验对比**涌现规范（Emergent）**与**一次性规范控制（Single-shot）**下的实现忠实度。

### 2.1 实验设置
- **平台**：Claude Code（Anthropic）和 Codex（OpenAI）
- **条件**：
  - Emergent：接收约60轮渐进式交互脚本，规范逐步披露
  - Single-shot：会话初始即接收完整论文PDF
- **样本**：20篇论文（ICML 2025和NeurIPS 2025各10篇），每平台每条件各运行一次，共 **80次运行**

### 2.2 评估指标
- **语义忠实度**：Mean Component Faithfulness（MCF）
  $$ \text{MCF} = \frac{1}{N}\sum_{i=1}^N s_i, \quad s_i \in \{0,1,2,3,4\} $$
- **结构整合**：Dependency Integration Ratio（DIR）
  $$ \text{DIR} = \frac{|E_{\text{used}}|}{|E_{\text{total}}|} $$
  衡量独立模块的公共符号被下游集成代码实际复用的比例
- **综合指标**：Implementation Faithfulness（IF50）
  $$ \text{IF50} = \frac{1}{2}\left(\frac{\text{MCF}}{4}\right) + \frac{1}{2}\text{DIR} $$
  范围 [0,1]，作为主要终点指标

### 2.3 主要结果（Table 3, Figure 2）
| 平台 / 条件 | MCF | DIR | IF50 |
|-------------|-----|-----|------|
| Claude Code / Emergent | 2.718 | 0.149 | 0.414 |
| Claude Code / Single-shot | 3.031 | 0.303 | 0.530 |
| Codex / Emergent | 3.242 | 0.148 | 0.479 |
| Codex / Single-shot | 3.245 | 0.289 | 0.550 |

- **SLUMP 存在性**：
  - Claude Code：Single-shot 在 **16/20** 篇论文上更优，平均 IF50 差距 **+0.116**（Wilcoxon $p=0.0003$）
  - Codex：Single-shot 在 **14/20** 篇论文上更优，平均 IF50 差距 **+0.071**（$p=0.012$）

- **损失分解**（平台差异）：
  - **Claude Code**：语义和结构双降（MCF：3.031→2.718；DIR：0.303→0.149）
  - **Codex**：语义损失微小（MCF：3.245→3.242），但结构损失显著（DIR：0.289→0.148）

### 2.4 测试通过率的局限性（Figure 3）
- **发现**：测试通过率（Test Pass Rate）与 IF50 相关性低
- **含义**：代理自编写的测试可能验证"已产生的实现"而非"预期的设计"，**执行指标不足以检测 SLUMP**

### 2.5 定性案例分析（Table 4）
以 **DualEquiNet** 任务为例，展示早期实现的 `equivariant_coordinate_update.py` 模块在最终集成中被绕过（改为不兼容的 MLP 路径），导致该组件评分从 Single-shot 的 **4（Faithful）** 降至 Emergent 的 **2（Simplified）**。

## 3. 缓解实验：ProjectGuard 评估

评估外部项目状态层对 SLUMP 的缓解效果，对比 **Emergent** vs **Emergent+ProjectGuard**。

### 3.1 实验设计
- **机制**：ProjectGuard 维护语义状态（设计承诺）和结构状态（仓库骨架），在每轮编码前注入兼容性感知的项目简报，必要时触发主动重启
- **恢复率计算**：
  $$ \text{Recovery}_F = \frac{F(R^{\text{em+pg}}) - F(R^{\text{em}})}{F(R^{\text{ss}}) - F(R^{\text{em}})} \times 100\% $$

### 3.2 Claude Code 结果（SLUMP 较严重的平台）
- **MCF 恢复**：从 2.718（Emergent）提升至 **3.000**，恢复 **90%** 的规格瓶颈差距（vs Single-shot 3.031）
- **组件级改善**：
  - 完全忠实组件（Score 4）：118 → **181**（+53%）
  - 严重失败（Score ≤1）：72 → **49**（-32%）
- **IF50**：在 **15/20** 篇论文上实现正向恢复（Table 6）
- **DIR**：在 13/20 篇论文上改善（中位数 +12%）

### 3.3 Codex 结果
- **MCF**：改善微小（+0.05），与基线差距小（符合预期）
- **DIR**：在 **15/19** 篇可评估论文上改善，平均相对提升 **76%**（中位数 +55%），表明结构状态管理在改善模块整合方面的平台无关性

### 3.4 开销分析（Table 6）
- **外部状态大小**：平均 390 KB（Claude Code）/ 286 KB（Codex）
- **压缩事件**：Claude Code 上压缩事件中位数变化 -1（无额外压力）；Codex 上增加 23 次（因主动重启机制产生多个短会话，而非单会话内压力增加）

## 4. 基准资产人工审计（Appendix A.3）

对5篇采样论文进行人工审计，验证：
- 规范保留：Canonical specification 准确保留论文数学内容
- 轨迹一致性：潜在轨迹（latent trajectory）时间连贯且精确收敛至规范
- 请求充分性：编码请求对无法访问隐藏基准资产的代理足够具体

基于审计结果修订提示模板一次后冻结构建流程，确保基准资产质量。

- **跨领域迁移**：软件工程系统（如分布式系统、编译器）、数据科学 pipeline、科学计算（如计算物理/生物）中的涌现规范场景

## 总结

该论文围绕**长时程编码代理在渐进式规范披露场景下的实现忠实度损失**展开研究，主要内容可概括如下：

## 1. 研究动机与核心问题

现有编码代理基准测试（如 PaperBench、MLRBench 等）普遍假设**完整的任务规范在会话初始即已提供**（upfront specification）。然而，真实研究编码工作流程中，目标系统通常通过多轮交互**逐步涌现**（emergent specification）：早期探索替代方案，中期在部分规范下实现组件，后期整合为完整系统。

这种设定对代理提出**规范跟踪**（specification tracking）要求：必须在长会话中保留持久的设计承诺（数学公式、架构约束、接口契约等），并随代码库演进保持这些承诺。论文识别并量化了**涌现规范下的忠实度损失**（Faithfulness Loss Under Emergent Specification, SLUMP）：

$$\text{SLUMP}_F(p, a) = F(R_{p,a}^{\text{ss}}) - F(R_{p,a}^{\text{em}})$$

其中 $R^{\text{ss}}$ 为一次性获得完整规范时的实现，$R^{\text{em}}$ 为渐进获得规范时的实现，$F$ 为忠实度度量。

## 2. 基准测试设计

论文构建了针对涌现规范场景的评估基准，包含：
- **20篇近期ML论文**（ICML 2025和NeurIPS 2025各10篇），提取为**371个原子可验证组件**
- **渐进式交互脚本**：每篇论文约60轮编码请求，从模糊想法逐步收敛至完整方法，且**不透露原始论文**
- **五级忠实度评分**：
  - 0（Absent）：无实现
  - 1（Wrong）：逻辑错误
  - 2（Simplified）：降级/近似实现
  - 3（Equivalent）：功能等价但形式不同
  - 4（Faithful）：与规范紧密匹配
- **暴露审计**：验证组件可从可见交互中推断（恢复率99.4%），确保评估公平性

## 3. 实验发现

在 Claude Code 和 Codex 两个长时程编码平台上的对比实验显示：

| 维度 | Claude Code | Codex |
|------|-------------|-------|
| **整体忠实度**（IF50） | Single-shot 在16/20论文更优（差距+0.116） | Single-shot 在14/20论文更优（差距+0.071） |
| **语义忠实度**（MCF） | 显著下降（3.031→2.718） | 几乎不变（3.245→3.242） |
| **结构整合**（DIR） | 显著下降（0.303→0.149） | 显著下降（0.289→0.148） |

关键发现：
- **SLUMP 在两个平台上均显著存在**，但损失构成不同：Claude Code 在语义和结构双维度受损，Codex 主要损失结构整合
- **执行指标（测试通过率）与忠实度相关性低**，说明代理自编写的测试无法验证实现是否符合预期设计

## 4. 缓解方案：ProjectGuard

作为针对性缓解的案例研究，论文提出 **ProjectGuard**——一种外部项目状态层，无需修改底层模型即可改善规范跟踪：

- **语义状态**：记录设计承诺、实现决策和支持资源，采用保守更新策略（仅确认用户接受的承诺）
- **结构状态**：维护仓库骨架（文件、类/函数签名），直接从 Git 历史派生
- **兼容性感知预测**：每轮编码前，结合请求历史与双状态生成项目简报，识别需保留的模块和兼容性约束
- **主动重启**：当剩余上下文不足以支持复杂集成时，触发新会话并注入渲染后的项目状态

在 Claude Code 上的实验表明，ProjectGuard 可：
- 恢复 **90%** 的忠实度差距（MCF 从2.718提升至3.000，接近单次规范控制的3.031）
- 将完全忠实组件数从118提升至181（+53%）
- 将严重失败数从72降至49（-32%）

## 5. 主要贡献

1. **基准贡献**：首个针对涌现规范编码的评估基准，结合长交互脚本、组件级忠实度评分和暴露审计机制
2. **实证发现**：证明渐进规范披露相对单次规范控制会系统性降低实现忠实度（SLUMP），且该损失在结构整合维度具有跨平台稳健性
3. **技术方案**：展示通过显式维护外部语义与结构项目状态，可显著缓解 SLUMP，为长时程编码代理的规范跟踪能力提供可行改进路径

论文代码与基准已开源，旨在推动将**规范跟踪**作为长时程编码代理的独立评估维度。
