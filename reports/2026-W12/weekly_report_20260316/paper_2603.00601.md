# Theory of Code Space: Do Code Agents Understand Software Architecture?

**arXiv**: [2603.00601](https://arxiv.org/abs/2603.00601) · [PDF](https://arxiv.org/pdf/2603.00601)  
**领域**: Agent  
**作者**: Sapunov

## 摘要

> 本文提出了一种名为'代码空间理论'（ToCS）的新基准测试，用于评估代码智能体在探索代码库时构建、维护和更新架构信念的能力。论文通过程序生成的代码库和部分可观测性设置，系统地研究了多种前沿大语言模型在软件架构理解方面的表现，发现了模型在主动探索、信念状态维护等方面的显著差异。论文开源了ToCS基准测试代码，为相关研究提供了有价值的工具。

## 详细分析

> **社区热度**: ⭐ 2 (来自 papers.cool)

## 问题定义

这篇论文试图解决的核心问题是：**AI代码代理（Code Agents）在复杂、多文件软件工程任务中表现出的架构理解能力缺失**。

具体而言，论文针对以下关键现象展开研究：

- **能力鸿沟**：当前AI代码代理在孤立任务（如编写独立函数、修复局部化缺陷）上表现卓越，但在需要理解数十个相互依赖模块之间关系的真实代码库修改任务中表现不佳。

- **根因假设**：论文假设这些失败并非源于简单的知识缺乏，而是源于**无法构建、维护和更新连贯的架构信念状态**（coherent architectural beliefs）——即在部分可观察的代码库探索过程中，代理无法形成关于模块依赖关系、横切不变量和设计意图的结构化内部表征。

- **评估缺失**：现有基准（如SWE-bench）主要衡量最终补丁的正确性，而非代理在探索过程中对架构理解的演化过程；缺乏对"主动构建认知地图"这一能力的系统性评估。

为解决这个问题，论文提出了**Theory of Code Space (TOCS)**——首个评估代码代理在部分可观察环境下主动构建、修订和利用架构信念能力的基准框架，通过以下方式诊断代理的架构理解能力：

1. **程序化生成**具有控制架构结构的代码库，包含四种类型边（IMPORTS、CALLS_API、DATA_FLOWS_TO、REGISTRY_WIRES）和植入的架构约束；
2. **部分可观察探索**：代理在预算限制下主动选择打开文件，模拟真实开发中的信息获取过程；
3. **周期性信念探测**：通过结构化JSON要求代理外化其当前架构信念，形成理解演化的时间序列数据；
4. **架构约束发现**：评估代理发现诸如"禁止依赖""仅通过接口访问"等显式架构规则的能力。

论文的初步实验揭示了严重的**信念外化瓶颈**和**信念状态不稳定性**——即使某些模型展现出代码理解行为，也无法可靠地将内部知识序列化为结构化表示，或在探测之间灾难性地遗忘先前发现的组件，这表明**信念状态维护本身是非平凡的能力**。

## 相关工作

论文的相关研究主要集中在三个领域：

### 1. 代码生成基准（Code Generation Benchmarks）

| 研究工作 | 核心内容 | 与TOCS的区别 |
|---------|---------|-------------|
| **SWE-bench** [Jimenez et al., 2024] | 在真实GitHub仓库中评估缺陷修复能力，衡量补丁正确性 | 衡量最终输出而非架构理解的演化过程 |
| **ContextBench** [Li et al., 2026] | 记录代理轨迹，针对人工验证的黄金上下文评分上下文检索的精确率/召回率 | 衡量"看了什么"而非"对架构的信念是什么" |
| **SWE-ContextBench** [Zhu et al., 2026] | 测试跨任务经验复用能力 | 不关注信念状态的外部化 |
| **RepoBench** [Liu et al., 2024] | 评估仓库级代码自动补全 | 不涉及主动探索与信念构建 |
| **LoCoBench-Agent** [Qiu et al., 2025] | 评估长上下文软件工程中的交互，观察到"理解-效率权衡" | 未形式化为主动-被动差距（Active-Passive Gap），也不要求外部化可修订的架构信念 |
| **RefactorBench** [Masai et al., 2025] | 针对多文件重构，评估输出正确性 | 不探测信念状态，无探索预算限制 |

**关键差异**：这些基准均不要求代理**外部化可修订的架构信念状态**、不施加**探索预算**、也不针对**类型化依赖图与植入约束**进行评分。

### 2. 代码理解工具（Code Understanding Tools）

- **CodePlan** [Bairi et al., 2024]：利用静态分析依赖图增强LLM进行变更传播——这验证了本文的前提（代理需要架构地图但目前无法独立构建），而TOCS提供了诊断基准来测试此类方法是否真正改善了架构信念质量。
- **Aider's RepoMap** [Gauthier, 2024]：使用tree-sitter解析和PageRank构建仓库上下文。
- **Code World Models** [FAIR CodeGen team et al., 2025]：在 execution traces 上训练LLM以改进代码推理。

### 3. 空间推理（Spatial Reasoning）

- **Theory of Space (TOS)** [Zhang et al., 2026]：在网格世界环境中展示了**主动-被动差距**（Active-Passive Gap）和**信念惯性**（Belief Inertia）。TOCS将此框架移植到代码领域，并增加了空间基准中不存在的**架构约束发现**维度。
- **SpatialVLM** [Chen et al., 2024]、**Habitat** [Savva et al., 2019]、**OpenEQA** [Majumdar et al., 2024]：评估空间推理和具身问答，但不需要构建可修订的信念状态。
- **TOM-SWE** [Zhou et al., 2025]：建模SWE代理中用户的思维状态——与本文关注代理对代码库的信念形成互补。

### 理论基础

论文还引用了程序理解领域的经典研究：
- **Tolman [1948]**：提出"认知地图"（cognitive map）概念
- **Pennington [1987]** 与 **von Mayrhauser and Vans [1995]**：表明开发者构建分层的代码心理模型——TOCS将这一过程操作化并用于AI代理评估。

## 解决方案

论文通过提出 **Theory of Code Space (TOCS)** 框架，从**评估范式**、**环境设计**和**测量方法**三个层面系统性地解决该问题：

### 1. 形式化架构信念构建过程

将代码库理解重新定义为**在部分可观察环境下的潜在架构状态信念构建问题**：

- 定义 ground-truth 架构状态 $S = (G, I, C)$，其中 $G=(V,E)$ 为类型化依赖图（包含四种边类型），$I$ 为跨模块不变量，$C$ 为导出契约
- 明确代理需执行的三种操作：**Construct**（从部分观察构建信念）、**Revise**（环境突变时更新信念）、**Exploit**（利用信念执行下游任务）
- 通过周期性探测将潜在内部状态 $M_t(S)$ 外部化为可测量的结构化表示 $\hat{M}_t$

### 2. 程序化生成可控的评估环境

解决真实代码库难以控制变量和获取 ground truth 的问题：

**架构语法（Architecture Grammar）**
- 生成 Pipeline 架构的 Python 项目，包含 6–8 个语义连贯的处理阶段
- 植入**反平凡性措施**（anti-triviality）：注册表动态 wiring、适配器间接层、干扰模块、中性命名（mod_a.py 而非 extract.py）、隐藏不变量

**四类型边（Four Typed Edge Categories）**
反映不同的发现难度，强制代理超越语法分析：
- **IMPORTS**（$\sim$67%）：Python 导入语句，可通过 AST 解析发现
- **CALLS_API**（$\sim$17%）：运行时函数调用，需阅读函数体
- **REGISTRY_WIRES**（$\sim$9%）：配置驱动连接，需理解 importlib 动态加载逻辑
- **DATA_FLOWS_TO**（$\sim$7%）：数据流依赖，需理解编排逻辑

**植入可验证约束（Planted Invariants）**
- 植入 15–16 个结构化约束（禁止依赖、仅通过接口访问、验证链等）
- 每个约束具有规范形式 $(\text{type}, \text{src}, \text{dst}, \text{via}, \text{pattern})$ 和证据来源（测试、结构模式或文档）

### 3. 部分可观察性探索机制

模拟真实开发中的信息获取限制：

- **动作空间**：LIST（列出目录）、OPEN（打开文件，消耗预算）、SEARCH（仅返回路径+行号，无内容片段）、INSPECT（仅查看类型签名+文档字符串）、DONE
- **预算约束**：默认预算 $B=20$，迫使代理制定探索策略而非遍历全库
- **关键设计**：SEARCH 不返回内容片段，确保架构理解需要主动的 OPEN 决策；INSPECT 允许通过文档字符串低成本获取架构提示

### 4. 时间序列信念探测（Cognitive Map Probing）

解决"仅评估最终状态无法捕捉理解过程"的问题：

- **周期性探测**：每 $K=3$ 个动作中断代理，要求外化当前架构信念为结构化 JSON
- **零成本探测**：探测不消耗预算，确保测量不干扰探索策略
- **结构化输出** $\hat{M}_t$ 包含：
  - 组件信念：状态（已观察/已推断/未知）、目的、导出符号、类型化依赖边及置信度
  - 不变量信念：结构化规范形式及证据指针
  - 不确定性追踪：未探索区域列表

### 5. 多维度评估体系

**依赖关系指标（Dependency F1）**
- 严格匹配：要求 $(\text{source}, \text{target}, \text{type})$ 完全一致，且目标必须为具体文件路径（非目录级别）
- 区分粒度错误：惩罚正确的关系但错误的粒度（如报告目录级而非文件级边）

**架构约束发现（Invariant F1）**
- 通过结构化字段匹配（非文本相似性）评估约束发现能力
- 支持**松弛匹配**（relaxed matching）处理提示规范不足的情况

**效率曲线**
- **动作效率**：$AUC(F1 \text{ vs. 总动作数})$，奖励早期发现
- **观察效率**：$AUC(F1 \text{ vs. OPEN 次数})$，隔离每文件信息增益

**主动-被动差距分解（Active-Passive Gap Decomposition）**
将总差距 $APG_{total}$ 分解为：
- $APG_{selection}$：选择成本（被动-Oracle vs 主动）
- $APG_{decision}$：决策成本（被动-Replay vs 主动）

**信念修订评分（Belief Revision Score, BRS）**
- 环境突变后测量正确更新率，分解为：
  - **惯性**（Inertia）：已正确信念未更新
  - **影响发现**（Impact-discovery）：新发现的缺失元素
  - **轻信**（Gullibility）：无实际变化时的错误更新

### 6. 诊断性发现与改进路径

通过初步实验揭示具体瓶颈并提供解决方向：

- **信念外化瓶颈**：发现 GPT-5.3-Codex 与 Gemini 3 Flash 在 IMPORTS 召回率上存在 6 倍差距（69% vs 11%），证明即使"看到"相同内容，不同模型的外部化能力差异巨大
- **信念状态不稳定性**：发现 Gemini 2.5 Pro 在探测间灾难性遗忘（单步丢失 12 个正确边），而其更小版本 Flash 却保持完美稳定累积，揭示**信念状态维护本身是非平凡能力**
- **提示敏感性**：通过改进探测提示（添加每类型字段语义和成对分解说明），不变量 F1 从 0 提升至 0.78，证明评估框架需将提示视为一阶实验变量

该框架通过将"架构理解"从黑箱输出转化为可测量的**信念状态时间序列**，首次实现了对代码代理**主动认知地图构建能力**的系统性诊断。

## 实验验证

论文进行了以下实验来验证TOCS基准的区分能力和诊断价值：

### 1. 实验设置

**数据集**
- 使用程序化生成的3个中等复杂度代码库（seeds 42, 123, 999）
- 每个代码库包含27-30个模块，约70-84条依赖边，15-16个植入不变量

**环境参数**
- 探索预算：$B=20$（允许执行的动作数）
- 探测间隔：$K=3$（每3个动作进行一次信念外化探测）
- 动作成本：OPEN/SEARCH/INSPECT各消耗1，LIST/DONE消耗0

**提示版本**
- 所有LLM代理使用相同的系统提示和探测提示
- 实验对比了两种探测提示版本（旧版 vs 改进版），改进版添加了每类型字段语义、文件路径粒度说明和成对不变量分解示例

### 2. 评估方法

**规则基线（Rule-based Baselines）**
- **Oracle**：直接输出ground-truth图（理论上界，F1=1.0）
- **Config-Aware**：先打开配置/注册表文件解析模块引用，再按BFS跟随导入
- **Random**：列出根目录后随机打开文件直到预算耗尽
- **BFS-Import**：按广度优先跟随导入链打开文件

所有基线通过AST解析导入和配置引用构建认知地图。

**LLM代理**
- **GPT-5.3-Codex**：OpenAI代码专用推理模型（温度固定为1）
- **Claude Sonnet 4.6**：Anthropic前沿编码模型
- **Gemini 2.5 Flash**：Google推理优化轻量模型（"思考"模型）
- **Gemini 2.5 Pro**：Gemini 2.5 Flash的更大版本
- **Gemini 3 Flash**：Gemini 3系列轻量模型
- **Gemini 3.1 Pro**：Gemini 3系列旗舰模型

除GPT-5.3-Codex外，所有模型温度设为0。所有探测响应通过确定性修复解析器解析（零格式失败）。

### 3. 主要实验结果

**整体性能（Dependency F1）**
| 方法 | Dep F1 | Precision | Recall | 打开文件数 |
|------|--------|-----------|--------|------------|
| Oracle | 1.000 | 1.000 | 1.000 | — |
| Config-Aware | 0.577 | 0.736 | 0.475 | 13 |
| **GPT-5.3-Codex** | **0.676** | 0.782 | **0.597** | 15 |
| **Claude Sonnet 4.6** | **0.664** | **0.983** | 0.502 | 13 |
| Gemini 2.5 Flash | 0.470 | 0.642 | 0.373 | 14 |
| Gemini 3.1 Pro | 0.321 | 0.764 | 0.212 | 11 |
| Gemini 2.5 Pro | 0.242 | 1.000 | 0.138 | 12 |
| Gemini 3 Flash | 0.147 | 0.897 | 0.080 | 12 |

**关键发现：**
- GPT-5.3-Codex和Claude Sonnet 4.6超越所有基线（F1分别达0.676和0.664），而较弱LLM（Gemini 3 Flash，F1=0.147）低于简单启发式（Random，F1=0.538）
- Claude实现近完美精度（0.983）但保守召回（0.502）；GPT平衡精度与召回，打开更多文件（15个）
- Gemini 2.5 Pro虽达完美精度（1.0），但召回极低（0.138），显示极端保守主义

**边类型发现能力（Edge Type Recall）**
| 方法 | IMPORTS | CALLS_API | DATA_FLOWS_TO | REGISTRY_WIRES |
|------|---------|-----------|---------------|----------------|
| Config-Aware | 0.58 | 0.00 | 0.00 | 1.00 |
| BFS-Import | 0.25 | 0.00 | 0.00 | 0.00 |
| **GPT-5.3-Codex** | **0.69** | **0.15** | **0.31** | **1.00** |
| **Claude Sonnet 4.6** | 0.56 | **0.15** | 0.00 | **1.00** |
| Gemini 2.5 Flash | 0.47 | **0.18** | 0.00 | 0.37 |
| Gemini 3.1 Pro | 0.27 | 0.00 | **0.50** | 0.00 |

**关键发现：**
- LLM代理集体发现所有四种边类型，而基线最多发现两种（IMPORTS和REGISTRY_WIRES）
- GPT-5.3-Codex在IMPORTS（69%）和DATA_FLOWS_TO（31%）上领先
- Gemini 3.1 Pro在DATA_FLOWS_TO上达最高召回（50%），在一个代码库上完美发现所有6条阶段间数据流边
- Gemini 2.5 Flash发现基线无法看到的CALLS_API边（18%召回）

**架构约束发现（Invariant F1）**
- 使用改进提示后，LLM代理在松弛匹配下实现显著不变量发现：
  - Claude Sonnet 4.6：**0.778**
  - GPT-5.3-Codex：**0.739**
  - Gemini 2.5 Flash：0.517
  - Gemini 2.5 Pro：0.376
- 基线无法发现不变量（F1=0.000），因其无法推理跨领域约束

**效率分析（Action AUC）**
- Claude Sonnet 4.6在动作效率上领先（AUC=0.350），奖励早期发现
- GPT-5.3-Codex次之（0.306），显著高于Config-Aware（0.212）
- 即使文件覆盖相似，LLM代理因语义理解而实现更高效率

**信念状态稳定性分析**
- **Gemini 2.5 Flash**：在所有探测间保持零正确边丢失，实现纯粹单调累积
- **Gemini 2.5 Pro**：展现灾难性信念崩溃——在第9步构建合理地图（F1=0.33）后，单步丢失12条正确边（F1跌至0.09）
- **Gemini 3 Flash**： exhibit 严重近因偏差，每次探测仅报告3-5个最近检查的组件，完全丢弃早期发现
- **Gemini 3.1 Pro**：展现变量不稳定性，最佳代码库上单调累积（F1=0.458），最差代码库上崩溃至零边后部分恢复

**提示改进实验（Probe Prompt Ablation）**
对比旧版与改进版探测提示（仅提示不同，模型与代码库相同）：

| 模型 | 旧提示F1 | 新提示F1 | ΔF1 |
|------|----------|----------|-----|
| Gemini 2.5 Flash | 0.328 | 0.469 | +0.141 |
| GPT-5.3-Codex | 0.564 | 0.676 | +0.113 |
| Claude Sonnet 4.6 | 0.639 | 0.650 | +0.012 |

在probe_as_scratchpad模式下（代理保留JSON地图在上下文中），改进提示不仅提升序列化质量，还改变探索行为——GPT-5.3-Codex在新提示下于第16步后额外打开4个阶段模块，获得26条额外正确边。

**预算敏感性实验（Appendix C）**
测试不同预算$B \in \{10, 15, 20, 25\}$下的基线性能：
- $B=10$时，Config-Aware对Random的优势最大（3倍，0.175 vs 0.056）
- $B=25$时，Random收敛至Config-Aware水平（0.632 vs 0.626）
- 证实当前中等复杂度代码库在紧凑预算下最能区分探索策略

### 4. 实验限制
- 初步结果：每个模型-代码库对仅单次运行，无方差估计
- 单语言：仅Python（Pipeline架构）
- 单提示设计：所有LLM使用相同提示，未进行广泛的提示工程变体测试
- 中性命名：移除语义文件名可能使任务人为变难，但隔离了架构推理与词汇猜测

## 未来工作

基于论文的讨论与局限性部分，未来研究可沿以下维度展开：

### 1. 基准扩展与多样化

**架构模式扩展**
当前仅支持 Pipeline 架构，需扩展至：
- 事件驱动架构（Event-driven）
- 微服务架构（Microservices）  
- 插件系统（Plugin systems）
- 六边形架构（Hexagonal architecture）

**多语言支持**
当前仅生成 Python 代码，需为 TypeScript、Go、Java 等语言实现新的生成模板，检验跨语言的信念构建能力差异。

**真实代码库验证**
当前使用程序化生成的中性命名代码库（隔离架构推理与词汇猜测），未来需在真实 GitHub 仓库上验证，特别是包含有机复杂性、死代码和遗留代码的场景。

### 2. 评估模式完善

**REVISE 操作的完整实现**
v0.1 仅评估了 Construct 操作。需实现环境突变（$S \rightarrow S'$）后的信念修订评估：
- 植入文档过时（documentation staleness）场景，测试代理协调代码与文档矛盾的能力
- 测量信念修订评分（BRS），分解为惯性（Inertia-proper）、影响发现（Impact-discovery）和轻信（Gullibility）

**被动条件实验**
当前仅实现 Active 模式，需完成被动条件（Passive-Full, Passive-Oracle, Passive-Replay）以分解主动-被动差距（APG）：
- $APG_{selection}$：选择成本（信息检索策略）
- $APG_{decision}$：决策成本（观察利用效率）

### 3. 提示工程与信念外部化机制

**提示消融研究**
当前使用单一提示设计，需系统研究：
- Schema 详细程度对信念外化质量的影响
- 少样本示例（few-shot）数量与质量
- 思维链引出（chain-of-thought elicitation）策略
- 明确边类型决策规则（如"若同时满足 IMPORTS 和 CALLS_API，仅报告后者"）

**信念外部化训练**
探索专门优化目标，使模型忠实将架构知识序列化为结构化格式，而非仅依赖提示工程。

**信念状态维护机制**
针对观察到的"灾难性信念崩溃"（如 Gemini 2.5 Pro）与"完美稳定累积"（如 Gemini 2.5 Flash）的反直觉现象：
- 研究模型架构或训练目标如何影响信念状态稳定性
- 开发显式状态管理机制（持久化累积数据结构），替代依赖隐式上下文记忆

### 4. 混合架构与工具增强

**静态分析+语义分析混合**
结合 AST 级导入提取（确保结构完整性）与 LLM 语义分析（发现 DATA_FLOWS_TO 等语义边），验证 CodePlan、RepoMap 等工具是否真正改善架构信念质量。

**探索策略优化**
- 开发自适应预算分配策略（在覆盖广度与理解深度间权衡）
- 实现 FETCH_DOC 动作，测试代理何时选择查阅外部文档（README、ADR、OpenAPI 规范）

### 5. 评分方法论改进

**分层评分体系**
当前严格精确匹配（exact match）惩罚了语义正确但格式不符的答案（如目录级 vs 文件级边）。需实现：
- 语义等价性检测（partial credit for semantically equivalent answers）
- 规范化预测（normalizing predictions）后再比较

**粒度不匹配处理**
明确组件边界定义（测试文件、配置、__init__.py 是否包含），或实现多级粒度匹配。

### 6. 系统级能力评估

**下游任务性能（Exploit 操作）**
当前使用反事实探测作为代理，需测量信念质量与真实软件工程任务（如重构、缺陷修复）成功率的关联。

**预算与复杂度关系**
基于附录 C 的预算扫描结果（$B \in \{10,15,20,25\}$），研究：
- 不同代码库规模下的最优预算分配
- 复杂度临界点（何时代理能力出现相变）

**模型家族深度对比**
- 开源权重模型（Llama、Qwen、DeepSeek）的系统性评估
- 重复运行以估计方差（当前为单运行结果）
- 模型规模与信念稳定性的关系（小模型 Flash 优于大模型 Pro 的反常现象）

### 7. 文档生态建模

扩展生成器以包含独立文档文件（README、架构决策记录 ADR、API 规范），测试：
- 代理是否优先阅读文档或直接深入代码
- 文档-代码不一致时的信任决策机制
- 外部文档检索的预算成本效益分析

## 总结

这篇论文针对 AI 代码代理在复杂、多文件软件工程任务中表现出的**架构理解能力缺失**问题，提出了 **Theory of Code Space (TOCS)**——首个系统评估代码代理在部分可观察环境下主动构建、维护和修订架构信念能力的基准框架。

### 核心问题

当前大语言模型（LLM）在孤立代码生成任务（如 HumanEval）中表现优异，但在需要理解数十个相互依赖模块的真实代码库修改中表现不佳。论文假设这一差距源于代理**无法构建和维持连贯的架构信念状态**（coherent architectural beliefs），即缺乏对模块依赖、横切不变量和设计意图的结构化内部表征。

### TOCS 框架设计

论文通过以下设计将空间推理中的"认知地图"概念移植到软件工程领域：

**1. 程序化代码库生成**
- 生成中等复杂度的 Pipeline 架构 Python 项目（27–30 个模块）
- 引入四类型边反映不同发现难度：
  - **IMPORTS**：Python 导入语句（AST 可解析）
  - **CALLS_API**：运行时函数调用（需阅读函数体）
  - **REGISTRY_WIRES**：配置驱动动态 wiring（需理解 importlib 逻辑）
  - **DATA_FLOWS_TO**：数据流依赖（需理解编排逻辑）
- 植入 15–16 个可验证的架构约束（如禁止依赖、仅通过接口访问等）
- 采用反平凡性措施：中性命名、适配器间接层、干扰模块

**2. 部分可观察性探索**
- 代理在预算 $B=20$ 限制下通过工具（LIST, OPEN, SEARCH, INSPECT）主动探索
- SEARCH 仅返回路径不返回内容，确保架构理解需要主动的 OPEN 决策

**3. 时间序列信念探测**
- 每 $K=3$ 个动作要求代理外化当前架构信念为结构化 JSON
- 探测零成本（不消耗预算），测量内容包括：
  - 组件信念（状态、目的、导出符号、类型化依赖边及置信度）
  - 不变量信念（结构化规范形式）
  - 不确定性追踪

**4. 多维度评估体系**
- **Dependency F1**：严格匹配 $(\text{source}, \text{target}, \text{type})$ 三元组
- **Invariant F1**：结构化字段匹配（非文本相似性）
- **效率曲线**：$AUC(\text{F1 vs. 动作数})$，奖励早期发现
- **主动-被动差距分解**：将 $APG_{total}$ 分解为选择成本与决策成本
- **信念修订评分（BRS）**：测量环境突变后的信念更新能力（预留）

### 主要实验发现

在 3 个生成代码库上评估 4 个规则基线与 6 个前沿 LLM 代理（OpenAI、Anthropic、Google）：

**1. 性能分化显著**
- **GPT-5.3-Codex**（F1 = 0.676）与 **Claude Sonnet 4.6**（F1 = 0.664）超越所有基线（最佳基线 Config-Aware 为 0.577）
- 较弱模型（Gemini 3 Flash，F1 = 0.147）低于简单启发式（Random，F1 = 0.538）

**2. 语义边发现能力**
- LLM 代理集体发现所有四种边类型，包括基线无法发现的 **CALLS_API**（最高 18% 召回）和 **DATA_FLOWS_TO**（最高 50% 召回）
- Claude 与 GPT 实现 **REGISTRY_WIRES** 完美召回（100%），而基线仅能通过配置解析发现此类型

**3. 信念外化瓶颈**
- 相同观察输入下，模型间 IMPORTS 召回率差距达 6 倍（69% vs 11%），证明**信念外化能力**（将内部知识序列化为结构化格式）本身是非平凡能力

**4. 信念状态不稳定性（核心发现）**
- **Gemini 2.5 Pro** 展现灾难性信念崩溃：在步骤 9 构建合理地图（F1 = 0.33）后，单步丢失 12 条正确边
- **Gemini 3 Flash**  exhibit 严重近因偏差，仅保留最近 3–5 个组件
- **Gemini 2.5 Flash**（最小模型）实现零正确边丢失的完美单调累积，反直觉地优于其更大版本（2.5 Pro），表明信念维护非单纯规模函数

**5. 提示敏感性**
- 改进探测提示（添加每类型字段语义）后，不变量 F1 从 0 提升至 0.78，证实先前失败主要源于提示规范不足而非模型能力缺失

### 贡献与启示

**理论贡献**
- 首次将空间推理中的主动-被动差距（Active-Passive Gap）与信念惯性（Belief Inertia）框架系统移植到软件工程领域
- 引入**架构约束发现**作为代码领域特有的评估维度

**实践启示**
1. 当前代码代理需结合 AST 级结构提取与 LLM 语义分析
2. 需开发显式信念状态管理机制，替代依赖隐式上下文记忆
3. 信念探测提示应视为一阶实验变量，需版本控制与消融研究

**局限与开放方向**
- 当前仅支持 Python 与 Pipeline 架构，需扩展至多语言、多架构模式
- 仅评估 Construct 操作，REVISE（环境突变后的信念更新）待实现
- 结果基于单运行，需重复实验估计方差及开源模型评估
