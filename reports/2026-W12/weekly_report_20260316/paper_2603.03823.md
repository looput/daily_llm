## 摘要

> 本文提出了一种名为SWE-CI的新型基准测试，旨在评估大语言模型（LLM）智能体在持续集成（CI）环境中长期维护代码库的能力。该工作将代码生成评估范式从静态、短期的功能正确性转向动态、长期的代码可维护性，填补了现有基准（如SWE-bench）的空白。作者团队未明确标注来自知名机构，故省略背景介绍。

## 详细分析

> **社区热度**: ⭐ 9 (来自 papers.cool)

## 问题定义

这篇论文试图解决现有代码生成基准测试在评估范式上的根本性局限：**现有基准几乎只关注智能体编写功能正确代码的静态能力，而无法评估其在长期代码演进过程中维持代码质量的能力**。

具体而言，论文针对以下核心问题：

**1. 快照式评估与真实软件维护的脱节**
- 现有基准（如HumanEval、SWE-bench等）普遍采用"快照式"协议：智能体接收单一完整需求并产生一次性解决方案
- 这种范式无法捕捉软件维护的本质特征——真实软件成功依赖于复杂需求变更和长期功能迭代，而非一次性修复

**2. 代码可维护性的不可观测性**
- 在静态测试中，编写脆弱硬编码修复的智能体与编写干净可扩展代码的智能体可能通过相同的测试套件，二者的可维护性差异完全不可见
- 只有在代码库长期演进时（新需求到达、接口变化、模块扩展），早期设计决策的后果才会累积显现：技术债务导致后续修改越来越困难

**3. 缺乏对回归控制的评估**
- 现有基准无法衡量智能体在连续修改过程中避免引入回归（regression，即先前通过的测试在后续变更后失败）的能力
- 实验表明，当前大语言模型在长期维护场景中的零回归率（zero-regression rate）普遍低于0.25，暴露了这一评估空白

**4. 评估范式的转变需求**
- 基于Lehman定律（软件质量随维护进展而内在退化）和ISO/IEC 25010标准对可维护性的定义（软件可被有效修改而不引入缺陷的程度）
- 论文提出需要**从静态、短期的功能正确性评估转向动态、长期的可维护性评估**

为系统性解决上述问题，论文构建了**SWE-CI**（SoftWare Engineering – Continuous Integration）基准测试，通过模拟真实仓库平均233天、71个连续提交的演进历史，采用架构师-程序员双智能体持续集成循环，并引入EvoScore指标来量化智能体在长期演进中维持代码质量的能力。

## 相关工作

根据论文内容，相关研究可从以下五个维度进行梳理：

### 1. 单文件/单函数代码生成基准测试
- **HumanEval** [1] 与 **MBPP** [2]：建立了"单文件合成"（single-file synthesis）范式，要求模型基于文档字符串或简短描述生成独立的功能代码片段，奠定了代码生成能力的基础评估标准。
- **LiveCodeBench** [3]：通过 contamination-free 的评估方式，进一步扩展了单文件代码生成的评估范围，涵盖多语言和多领域场景。

**与本文的关系**：这类基准聚焦静态、一次性的代码合成，未能涵盖跨文件依赖和长期演进场景。

### 2. 仓库级代码生成基准测试
- **SWE-bench** [4]：引入了 "Issue-to-PR" 范式，要求模型在完整仓库上下文中理解 GitHub Issue 并生成补丁（patch），首次将评估粒度从单文件扩展到真实仓库级别。

**与本文的关系**：SWE-bench 虽涉及仓库上下文，但仍属快照式（snapshot-based）评估——智能体基于单一 Issue 生成一次性修复。SWE-CI 在此基础上演进，强调**连续多次提交**的长期维护过程。

### 3. 智能体交互与工具使用基准测试
- **Terminal-bench** [5]：将评估范围扩展至命令行界面（CLI）操作，测试智能体在终端环境中执行复杂任务的能力。
- **τ-bench (tau-bench)** [6]：聚焦于工具-智能体-用户交互（tool-agent-user interaction），评估多轮工具调用的场景。

**与本文的关系**：这类基准关注交互广度，而 SWE-CI 在此基础上引入了**持续集成循环（CI-loop）**的深度交互范式，通过架构师-程序员双智能体协作模拟真实软件团队的迭代开发流程。

### 4. 软件演化理论与质量标准
- **Lehman's Laws** [7]：揭示了"软件质量随维护进展而内在退化"的演化规律，为理解维护复杂性提供了理论基础。
- **Brooks Jr.** [8]：在《人月神话》中确立维护活动占软件生命周期成本 60%-80% 的经验数据，强调了长期维护在软件工程中的核心地位。
- **ISO/IEC 25010** [9]：将可维护性（maintainability）定义为"软件可被有效修改而不引入缺陷或降低现有质量的程度"，强调其只能通过连续修改来观测。

**与本文的关系**：SWE-CI 的理论框架直接建立在上述文献基础上，将软件工程领域对维护成本和演化规律的认知转化为可量化的评估指标（EvoScore）。

### 5. 智能体开发框架
- **iFlow CLI** [10]：作为实验中使用的默认智能体框架，提供了支持多轮工具调用和环境交互的基础设施。

**与本文的关系**：SWE-CI 的双智能体评估协议（Architect-Programmer）可部署于此类框架之上，但重点在于**协议设计**而非框架本身，强调通过角色分工实现持续集成。

## 解决方案

论文通过构建 **SWE-CI（SoftWare Engineering – Continuous Integration）** 基准测试，从**评估范式**、**度量指标**、**数据构建**和**评估协议**四个层面系统性解决该问题。

### 1. 评估范式：从快照式到演进式

论文提出**演进式评估范式（evolution-based evaluation）**，替代传统的快照式（snapshot-based）评估：

- **形式化定义**：定义两个核心函数：
  - $\text{require}_T: \mathcal{C} \times \mathcal{C} \to \mathcal{R}$，识别两个代码库之间的功能差距并生成需求文档
  - $\text{code}_T: \mathcal{R} \times \mathcal{C} \to \mathcal{C}$，根据需求修改代码库

- **动态迭代循环**：与快照式中静态需求 $r \equiv \text{require}_T(c_0, c^*)$ 不同，演进式在每次迭代中动态生成需求：
  $$r_i = \text{require}_T(c_i, c^*), \quad c_{i+1} = \text{code}_T(c_i, r_i)$$

  这种迭代确保早期修改的后果会传播到后续迭代，使智能体的长期决策质量可被观测。

### 2. 度量指标：Normalized Change 与 EvoScore

为解决传统二值化测试（通过/失败）无法捕捉回归（regression）和渐进式开发的问题，论文引入两个指标：

**Normalized Change** $a(c)$：
$$n(c) = \sum_{t \in T} \mathbb{I}(t, c)$$

$$a(c) = \begin{cases} 
\frac{n(c) - n(c_0)}{n(c^*) - n(c_0)} & \text{if } n(c) \geq n(c_0) \\
\frac{n(c) - n(c_0)}{n(c_0)} & \text{if } n(c) < n(c_0)
\end{cases}$$

其中 $n(c)$ 为代码库 $c$ 通过的测试数。该指标将改进（归一化到目标差距）和回归（归一化到基线）统一映射到 $[-1, 1]$ 区间，$a(c) = -1$ 表示破坏了所有初始通过的测试。

**EvoScore**（Evolution Score）：
$$e = \frac{\sum_{i=1}^N \gamma^i a(c_i)}{\sum_{i=1}^N \gamma^i}$$

通过未来加权平均（$\gamma \geq 1$），EvoScore 使后期迭代获得更高权重。这直接对应 ISO/IEC 25010 对可维护性的定义：**真正可维护的代码库应在演进过程中保持易于修改**。若智能体在早期牺牲速度换取更干净、可扩展的设计，将在后续迭代中获得更高奖励；反之，积累技术债务的智能体将看到性能逐步下降。

### 3. 数据构建：真实仓库的长期演进历史

SWE-CI 通过四步流程构建包含真实演进历史的数据集：

1. **仓库收集**：从 GitHub 筛选满足以下条件的 Python 仓库：维护时间 $\geq 3$ 年、Star $\geq 500$、包含配置和测试文件、采用宽松许可证（MIT/Apache-2.0），最终保留 4,923 个仓库。

2. **提交跨度提取**：保留主分支的线性提交历史，识别依赖不变的最大连续子序列，筛选代码修改行数 $\geq 1,000$ 的基线/目标（base/oracle）对，得到 8,311 个候选对。

3. **环境构建**：为每个目标代码库生成 Docker 镜像，通过自修复机制（自动注入缺失依赖）解决环境配置问题，保留 1,458 个候选。

4. **案例筛选**：运行测试确保基线代码库可启动，剔除测试通过数差异 $< 5$ 的样本，最终选择时间跨度和提交数排名前 100 的样本。

最终数据集包含 **100 个任务**，平均每个任务跨越 **233 天** 和 **71 个连续提交**，涉及至少 **500 行** 源代码修改（不含测试文件），确保捕捉实质性的长期演进而非琐碎增量变更。

### 4. 评估协议：Architect–Programmer 双智能体 CI 循环

为模拟真实软件团队的持续集成流程，论文设计**双智能体协议**：

**Architect 智能体**（架构师）：
- **输入**：当前代码与目标代码的测试差距
- **职责**：生成高层次需求文档
- **三步流程**：
  1. **Summarize**：审查失败测试，识别根本原因
  2. **Locate**：检查源码，将失败归因到具体实现缺陷
  3. **Design**：制定改进计划，生成需求文档
- **约束**：每次迭代最多提出 5 个最紧急需求（Incremental），使用自然语言描述期望行为而非具体实现（High-level）

**Programmer 智能体**（程序员）：
- **输入**：Architect 生成的需求文档
- **职责**：根据需求维护代码
- **三步流程**：
  1. **Comprehend**：理解高层次需求，转化为明确代码规范
  2. **Plan**：规划实现方案（如采用工厂模式等设计决策）
  3. **Code**：执行修改，满足需求

**CI 循环机制**：
从基线代码库 $c_0$ 开始，Architect 分析测试差距生成需求 $r_i$，Programmer 据此修改代码得到 $c_{i+1}$，运行测试验证，循环往复直至达到最大迭代次数（20轮）或通过所有目标测试。这种设计使**技术债务的累积效应**得以显现：早期设计决策的质量会在后续迭代中逐步暴露。

### 5. 关键创新：暴露维护能力的差异

通过上述设计，SWE-CI 解决了以下核心问题：

- **可维护性可观测性**：通过 $\gamma > 1$ 的 EvoScore，偏好长期稳定而非短期收益，使"编写干净代码"与"编写脆弱修复"的智能体产生可区分的表现差异。
- **回归控制评估**：引入**零回归率（zero-regression rate）**指标，衡量整个维护过程中未引入任何回归（先前通过的测试失败后失败）的样本比例，量化智能体在持续维护场景中的稳定性。
- **需求动态生成**：Architect 智能体从测试差距中动态提取需求，模拟真实场景中需求随代码状态演化的过程，而非依赖预先编写的静态提示。

## 实验验证

论文进行了大规模的实证评估，消耗了**超过100亿个token**，对18个来自8个不同提供商的先进模型进行了系统测试。实验设计围绕验证SWE-CI基准在评估长期代码维护能力方面的有效性展开，主要包含以下三个核心观察：

### 实验设置

- **测试框架**：使用 `pytest` 和 `pytest-json-report`，单次测试运行超时设置为3600秒
- **智能体框架**：采用 **iFlow CLI** 作为默认智能体执行框架
- **迭代限制**：双智能体评估协议的最大迭代次数设为**20轮**
- **评估对象**：覆盖8个提供商（包括Claude、GPT、GLM、DeepSeek、Qwen、Kimi、MiniMax、Doubao）共18个模型

### 实验发现

#### Observation 1：LLM代码维护能力呈加速进步趋势（图4）

通过对18个模型的横向对比发现：
- **代际进步显著**：同一提供商的系列模型中，新版本始终优于旧版本，特别是**2026年后发布的模型**相比前代展现出更大的性能跃升
- **能力范式转移**：这表明当前LLM的代码能力正快速从静态错误修复向**持续的长期代码维护**演进
- **领导者格局**：**Claude Opus系列**在整个观察期内保持绝对领先地位，**GLM-5**同样表现突出，位列第一梯队

#### Observation 2：不同提供商对代码可维护性的重视程度存在显著差异（图5）

通过调节EvoScore公式中的未来权重参数 $\gamma$ 进行敏感性分析：
- **$\gamma < 1$**：赋予早期迭代更高权重，偏好从代码修改中获得**即时收益**的模型
- **$\gamma > 1$**：赋予后期迭代更高权重，偏好为**长期改进**（即可维护性）优化的模型

**提供商策略分化**：
- **长期导向**：MiniMax、DeepSeek、GPT在$\gamma$增大时排名提升，表明其训练策略更重视代码的长期可维护性
- **短期导向**：Kimi和GLM在$\gamma$增大时排名下降，显示其更关注短期回报
- **均衡稳定**：Qwen、Doubao和Claude在不同$\gamma$设置下排名保持相对稳定

这一发现暗示不同提供商采用了差异化的训练策略，且同一提供商内部训练流程具有高度一致性。

#### Observation 3：当前LLM在长期维护中控制回归的能力仍显不足（图6）

通过**零回归率（zero-regression rate）**指标（即在整个维护过程中未引入任何回归的样本比例）评估模型稳定性：
- **普遍表现不佳**：大多数模型的零回归率**低于0.25**，表明在四分之三以上的任务中，模型至少破坏了一个先前通过的测试
- **顶尖模型例外**：仅有**Claude-opus系列**的两个模型零回归率超过0.5
- **核心挑战**：尽管LLM在基于快照的代码修改任务中表现优异，但在全自动、长期、多轮次的软件开发和维护场景中，**可靠避免回归**仍是一个重大挑战

这一结果凸显了SWE-CI的诊断价值：它能有效暴露那些在静态测试中表现良好、但在持续集成过程中因技术债务累积而逐渐失效的模型行为。

## 未来工作

基于论文内容，以下是可以进一步探索的研究方向：

### 1. 多语言与跨平台扩展
当前SWE-CI仅针对Python仓库构建。未来工作可将此评估范式扩展至**静态类型语言**（如Java、C++、Rust）和**动态脚本语言**（如JavaScript、TypeScript），考察类型系统对智能体长期维护能力的影响。此外，可探索**跨语言演进场景**（如Python与C++混合项目），评估智能体在复杂依赖环境下的维护表现。

### 2. 智能体架构的精细化设计
论文采用的Architect-Programmer双角色架构可进一步演化：
- **引入测试驱动角色（Tester Agent）**：专门负责生成回归测试和边界条件验证，形成"红-绿-重构"的完整TDD循环
- **引入代码审查角色（Reviewer Agent）**：在提交前进行静态分析和设计模式合规性检查，模拟真实团队的Code Review机制
- **记忆与知识累积机制**：当前每轮迭代相对独立，可探索让智能体维护**架构决策记录（ADR）**或**技术债务日志**，在后续迭代中主动避免重复错误

### 3. 技术债务的显式建模与量化
论文通过EvoScore间接反映技术债务，未来可构建**显式技术债务指标**：
- 引入**代码复杂度度量**（圈复杂度、认知复杂度）作为约束条件，评估智能体是否能在功能正确性与代码简洁性之间取得平衡
- 设计**债务累积函数**，量化早期"捷径"（hack）对后期迭代成本的指数级影响，建立更精细的数学模型
- 探索**重构操作**的自动识别与评估，区分"功能性修改"与"纯重构"对 EvoScore 的不同贡献

### 4. 针对长期维护的专门训练方法
实验结果显示不同厂商模型在可维护性上存在显著差异，暗示训练数据分布的影响。可探索：
- **课程学习策略**：按演进时长或提交数量逐步增加难度，训练模型理解长期后果
- **强化学习微调**：以EvoScore作为延迟奖励信号（而非即时测试通过率），通过RLHF或DPO方法对齐模型行为与长期维护目标
- **历史感知预训练**：在预训练阶段引入代码库的时序演化数据（commit序列），增强模型对软件演化的内在理解

### 5. 回归控制的机制设计
当前模型零回归率普遍偏低（<0.25），亟需针对性研究：
- **影响分析（Impact Analysis）机制**：开发自动工具帮助智能体预测修改对现有测试的潜在影响范围，类似工业界的测试选择（Test Selection）技术
- **回归测试自动生成**：研究智能体如何为新增功能自动生成Companion Test，确保新代码的鲁棒性同时不破坏旧行为
- **防御性编程策略**：训练模型采用更保守的修改策略（如保留向后兼容的包装器、使用功能开关等），优先保证稳定性

### 6. 人机协作与混合智能
探索人类开发者与AI智能体的协作模式：
- **角色互换研究**：人类担任Architect、AI担任Programmer，或反之，对比不同分工下的维护效率
- **交互式演进**：允许人类在关键节点介入（如架构决策点），评估人机协同是否优于纯自动化的CI循环
- **知识转移**：研究智能体如何从人类维护者处学习隐式的维护经验（如"何时应该重构而非修补"）

### 7. 真实工业场景的复杂性
当前基准环境相对隔离，可向更真实的DevOps环境扩展：
- **依赖演化场景**：模拟外部依赖库（如PyTorch、Django）的升级过程，评估智能体处理**破坏性变更（Breaking Changes）**的能力
- **并发与冲突解决**：模拟多开发者并行修改场景，评估智能体处理合并冲突（Merge Conflicts）和集成冲突的能力
- **性能回归检测**：除功能测试外，引入性能基准测试（Benchmark），评估维护过程中时间/空间复杂度的退化

### 8. 可解释性与诊断工具
开发专门工具解释智能体的维护行为：
- **决策溯源**：追踪Architect生成特定需求的原因，或Programmer选择特定设计模式的依据
- **失败模式分类**：建立回归失败的类型学（如API误用、状态污染、边界条件遗漏），为模型改进提供细粒度反馈
- **可视化仪表盘**：实时展示技术债务积累曲线、测试覆盖率变化趋势等，增强评估的可解释性

## 总结

本文提出 **SWE-CI（SoftWare Engineering – Continuous Integration）**，首个基于持续集成循环的仓库级基准测试，旨在将大语言模型（LLM）代码生成的评估范式从**静态功能正确性**转向**动态长期可维护性**。

### 1. 研究背景与核心问题

现有代码生成基准（如 HumanEval、SWE-bench）普遍采用**快照式评估（snapshot-based evaluation）**：智能体接收单一需求，生成一次性解决方案。这种范式存在根本性局限：

- **可维护性不可见**：编写脆弱硬编码修复的智能体与编写干净可扩展代码的智能体可能通过相同测试套件，其差异仅在长期演进中显现
- **忽视维护成本**：真实软件 60%-80% 的成本来自维护（Lehman 定律揭示软件质量随维护退化），但现有基准无法评估智能体在长期迭代中控制系统性质量退化的能力
- **回归控制缺失**：无法衡量智能体在连续修改中避免**回归（regression）**（先前通过的测试后失效）的能力

### 2. SWE-CI 评估框架

#### 演进式评估范式
定义两个核心函数：
- $\text{require}_T: \mathcal{C} \times \mathcal{C} \to \mathcal{R}$，识别当前代码库 $c_i$ 与目标代码库 $c^*$ 的功能差距，动态生成需求 $r_i = \text{require}_T(c_i, c^*)$
- $\text{code}_T: \mathcal{R} \times \mathcal{C} \to \mathcal{C}$，根据需求迭代更新代码库 $c_{i+1} = \text{code}_T(c_i, r_i)$

早期修改的后果通过迭代传播，使长期决策质量可被观测。

#### 度量指标
- **Normalized Change** $a(c)$：统一量化改进与回归的细粒度指标
  $$a(c) = \begin{cases} 
  \frac{n(c) - n(c_0)}{n(c^*) - n(c_0)} & \text{if } n(c) \geq n(c_0) \\
  \frac{n(c) - n(c_0)}{n(c_0)} & \text{if } n(c) < n(c_0)
  \end{cases}$$
  其中 $n(c)$ 为通过测试数，$a(c) \in [-1, 1]$，$-1$ 表示破坏所有基线测试。

- **EvoScore**：基于 ISO/IEC 25010 可维护性定义的**未来加权**评估指标
  $$e = \frac{\sum_{i=1}^N \gamma^i a(c_i)}{\sum_{i=1}^N \gamma^i}, \quad \gamma \geq 1$$
  后期迭代权重更高，奖励为长期可扩展性牺牲短期速度的智能体，惩罚积累技术债务的行为。

#### 数据构建
从 4,923 个 GitHub 仓库筛选，经过依赖不变性分析、环境自修复构建和多层过滤，形成 **100 个任务**：
- 平均跨度 **233 天**，**71 个连续提交**
- 每次任务涉及 **≥500 行** 源代码修改（不含测试文件）
- 提供预构建 Docker 环境确保可复现性

#### Architect–Programmer 双智能体协议
模拟真实软件团队的 CI 循环：
- **Architect 智能体**：分析测试差距，执行 Summarize-Locate-Design 三步流程，生成**高层次、增量式**（1-5 条）需求文档
- **Programmer 智能体**：执行 Comprehend-Plan-Code 三步流程，依据需求文档实现代码修改，避免直接面向测试硬编码

通过最多 20 轮迭代，智能体需将基线代码库演进至目标状态。

### 3. 实验发现

对 18 个模型（8 个提供商）消耗超 **100 亿 token** 的评估揭示：

- **能力快速演进**：2026 年后发布的模型展现显著性能跃升，**Claude Opus** 系列持续领先，表明 LLM 正从静态修复向长期维护能力扩展
- **策略分化显著**：通过调节 $\gamma$ 分析发现，MiniMax/DeepSeek/GPT 倾向长期收益（$\gamma>1$ 时排名提升），而 Kimi/GLM 偏向短期回报，反映不同厂商训练策略差异
- **回归控制薄弱**：**零回归率**（全程无回归的样本比例）普遍低于 0.25，仅 Claude Opus 系列超过 0.5，表明当前 LLM 在全自动长期维护中仍难以可靠避免质量退化

### 4. 主要贡献

- **范式创新**：首次建立基于持续集成循环的仓库级评估框架，使代码**可维护性**（而非仅功能正确性）成为可量化、可比较的核心指标
- **基准数据**：提供包含真实长期演进历史（233 天/71 提交）的高质量数据集，填补长期维护评估空白
- **诊断价值**：EvoScore 和零回归率指标能有效暴露智能体在长期演进中的技术债务累积行为，为模型改进提供细粒度反馈
